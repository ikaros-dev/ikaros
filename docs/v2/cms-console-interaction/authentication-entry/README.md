# 登录、认证与首次初始化交互规格

> 本目录描述 CMS Console 登录前入口、首次部署初始化、普通登录、Email OTP、Step-up Verification、账号恢复与认证失效场景。它属于全局入口能力，不在登录后的左侧业务菜单中显示。

## 1. 全局认证入口规则

- 未认证访问任意 `/console/**` 受保护路由时，跳转到 `/login`，并携带安全的原始目标地址用于登录成功后返回。
- Return URL 只允许站内受信路径，禁止任意外部 URL，避免开放重定向。
- 已认证用户访问 `/login` 时，默认跳转到 `/console/dashboard`；存在合法 Return URL 时优先返回原目标。
- 首次启动且系统尚未完成初始化时，所有 Console 入口统一进入 `/setup`，不得展示普通登录页造成“没有账号可登录”的死路。
- 认证页面不显示 Console 左侧导航和后台业务信息，只显示必要品牌、环境标识、帮助/语言/主题入口。
- 认证错误文案避免确认某个用户名、邮箱或账号是否存在。

## 2. 首次部署初始化

**路由：** `/setup`

### 2.1 进入条件

后端返回 `INITIALIZATION_REQUIRED` 或等价初始化状态时显示。初始化完成后该路由必须由后端拒绝再次执行初始化，而不是只依赖前端隐藏。

### 2.2 页面布局

桌面端使用居中宽卡片或 Stepper，最大内容宽度约 720–840 px。

顶部：
- Ikaros 标识。
- 标题 `初始化 Ikaros`。
- 当前部署环境/服务器名称安全摘要。
- 步骤指示器。

### 2.3 初始化步骤

#### 步骤 1：欢迎与环境检查

卡片展示：
- Ikaros 版本。
- 数据库连接状态。
- 工作目录/持久化存储基础状态，仅显示非敏感路径摘要。
- 必要迁移状态。
- 系统时间与时区。

存在阻断问题时显示 Error Banner，并提供 `重新检查`。阻断问题未解决不得进入下一步。

#### 步骤 2：创建初始管理员

字段：
- 用户名：必填，显示命名约束。
- 显示名称。
- 邮箱：按 V2 初期 Email OTP / 恢复策略要求设置为必填或明确提示功能影响。
- 密码：必填。
- 确认密码：必填。

密码输入：
- 默认遮罩。
- 显示/隐藏只影响当前字段。
- 实时展示长度、策略要求和强度说明。
- 不把密码写入 URL、日志、遥测、浏览器历史或页面标题。

#### 步骤 3：安全与恢复准备

根据当前部署能力展示：
- Email OTP 是否已配置可用。
- 恢复方式状态。
- Session 默认策略摘要。
- `稍后配置` 仅在后端策略允许时出现，并明确说明缺失能力带来的风险。

若邮件发送能力已配置，可提供 `发送测试邮件`。测试结果只展示成功/失败与安全错误摘要，不回显密钥或 SMTP 密码。

#### 步骤 4：基础偏好

字段：
- 默认语言。
- 默认时区。
- 日期/时间格式。
- 主题：跟随系统 / 浅色 / 深色。

这些设置作为初始管理员个人偏好；系统级默认值需要明确区分，避免一个人的选择意外成为所有用户的全局配置。

#### 步骤 5：确认并初始化

摘要卡展示：
- 将创建的管理员用户名/显示名称。
- 邮箱安全摘要。
- 时区/语言。
- 当前可用恢复/验证方式。

主按钮 `完成初始化`。

交互：
- 提交期间按钮进入 Loading，不允许重复提交。
- 初始化是幂等或受服务端一次性状态保护；网络超时后先查询初始化状态，不盲目再次创建管理员。
- 成功后进入登录态或要求重新登录，由后端安全策略决定；页面必须明确结果。

## 3. 登录页

**路由：** `/login`

### 3.1 页面结构

桌面端采用居中认证 Card；移动端全宽单栏。

Card 从上到下：
1. Ikaros 标识和 `登录 Ikaros`。
2. 可选环境 Chip。
3. 账号输入。
4. 密码输入。
5. `记住此设备/保持登录` 选项，仅在后端策略支持时展示。
6. `登录` Filled Button。
7. `忘记密码/无法登录` Text Button。
8. 外部身份提供方区域，仅在部署已启用时展示。

### 3.2 账号与密码

账号字段接受后端支持的用户名/邮箱等登录标识，但占位文案只写实际支持类型。

密码字段：
- 默认遮罩。
- 提供独立 Reveal Icon。
- Enter 在账号和密码完整时提交。
- 登录进行中锁定重复提交，但不清空输入。

### 3.3 登录结果

成功：
- 若无需进一步验证，进入 Return URL 或 `/console/dashboard`。
- 若要求 OTP/MFA，进入验证步骤且保留受保护的认证事务 ID，不把密码继续保留在页面状态中。
- 若账号需要安全动作（如强制改密），进入对应完整流程。

失败：
- 普通凭据失败统一显示 `账号或凭据不正确` 等不枚举账号存在性的文案。
- 网络/服务器失败独立提示，避免让用户误以为密码错误。
- 触发限流时展示剩余等待时间的粗粒度信息；不得暴露安全策略内部阈值。
- 账号锁定时按策略展示恢复入口，但不泄露更多账号信息。

## 4. Email OTP 与二次验证

**路由：** `/login/verify` 或认证事务内的独立步骤。

> V2 初期安全设计中的 SVL-1 使用 Email OTP。后续 SMS、证件、人脸等方式出现时复用同一验证交互骨架，不应为每种方式复制完全不同的页面。

### 4.1 页面字段

- 标题 `验证你的身份`。
- 说明：验证码发送到了掩码后的目标，例如 `n***@example.com`。
- 6 位或后端定义长度的 OTP 输入组件。
- `验证` 主按钮。
- `重新发送` Text Button + 倒计时。
- `使用其他方式`，只有真正存在其他已配置方式时展示。
- `返回登录`。

### 4.2 OTP 交互

- 支持整串粘贴，并自动分配到各位输入框。
- 输入完成后可自动提交，但必须提供明确 Loading 状态并避免多次请求。
- 错误时保留焦点并清空或选中无效 OTP，具体按安全策略。
- 重新发送后旧码失效与否以服务端策略为准，界面不得做错误保证。
- 达到尝试限制后进入冷却/恢复流程。

## 5. Step-up Verification

高风险操作触发 Step-up 时使用统一验证流程，而不是把用户直接踢回登录页。

### 5.1 触发形式

短流程使用 Modal Dialog；需要多步骤验证/恢复时使用独立安全页面。

Dialog 内容：
- 标题 `需要再次验证身份`。
- 明确原因，例如 `轮换系统签名密钥前需要更高等级验证`。
- 当前动作名称。
- 要求的 SVL 或验证方式，用用户可理解的文字表示。
- `开始验证` / `取消`。

### 5.2 成功后的返回

- 验证成功后返回原操作上下文，并继续执行或重新展示最终确认。
- Step-up 只提升验证保证等级，不新增任何业务 Permission。
- 验证窗口过期后再次执行高风险动作重新触发验证。

## 6. 忘记密码与账号恢复

**入口：** 登录页 `无法登录`。

### 6.1 恢复发起

字段：用户名/邮箱等后端支持的恢复标识。

提交后统一显示：
`如果该账号存在且已配置恢复方式，我们会发送下一步说明。`

不得通过成功/失败文案确认账号是否存在。

### 6.2 恢复验证

按后端策略使用 Email OTP、恢复材料或管理员辅助恢复。

页面必须显示：
- 当前恢复阶段。
- 可用验证方式的安全摘要。
- 失败/过期/重试状态。
- 返回登录入口。

### 6.3 重设密码

字段：新密码、确认新密码。

完成前摘要说明：
- 是否撤销其他 Session。
- API Token / 设备授权是否受影响，由后端策略明确。
- Secure Domain 密钥恢复与普通登录密码重置不是同一概念，不能用一个模糊按钮混合执行。

## 7. 会话过期、撤销与重新登录

### 7.1 Access Session 过期

API 返回认证失效时：
- 如果可安全刷新 Session，先执行无感刷新。
- 刷新失败则打开 `登录已过期` Dialog 或进入 `/login`。
- 保存中的普通表单应尽量保留非敏感草稿；私密/密码域按安全策略清除解密状态。

`登录已过期` Dialog：
- 说明 `你的登录状态已失效，需要重新登录`。
- `重新登录` 主按钮。
- `退出` 次按钮。

重新登录成功后返回原路由；对于非幂等提交，不自动重放先前请求，而是恢复表单并要求用户再次确认提交。

### 7.2 Session 被管理员或安全策略撤销

收到撤销事件时立即：
- 停止后续受保护请求。
- 清除 Token/受保护缓存。
- 锁定 Private Notes / Password Vault 等 Secure Session。
- 显示统一 Session 已失效说明。

## 8. 外部身份提供方

仅在实际启用 OAuth/OIDC 等提供方时显示。

按钮包含提供方图标、显示名称和 `使用 … 登录`。

规则：
- 登录跳转前保存安全 Return URL。
- 回调处理中显示独立 `正在完成登录` 状态。
- 提供方取消、拒绝授权、账号未绑定分别给出可理解错误，不展示原始 OAuth 错误堆栈。
- 第一次外部登录需要绑定/创建账号时进入明确的确认流程，不静默生成高权限账号。

## 9. 认证页面主题、语言与无障碍

- 登录前允许切换语言和浅色/深色/跟随系统主题。
- 认证 Card 仍满足 WCAG 可读性和键盘操作要求。
- OTP、密码错误不能只用红色表示。
- 密码 Reveal、返回、重新发送等 Icon/Button 均具有 Accessible Name。
- 浏览器自动填充使用正确的 `autocomplete` 语义；新密码与当前密码必须区分。

## 10. 安全边界

- 前端永远不保存 Root Key、KEK、恢复密钥明文等受保护密码学材料。
- Access Token/Refresh Token 的存储方式由安全设计决定，禁止因为前端方便直接落入普通 LocalStorage。
- 认证页不得把账号、邮箱、OTP、Token、Return 中的敏感 Query 发送到通用分析系统。
- 登录、恢复、Step-up、初始化管理员等安全动作必须产生后端 Security Audit；审计不记录密码、OTP 或 Secret 明文。
- 前端展示成功不等于完成安全判定，最终状态以服务端认证/授权/Verification Policy 为准。
