# Ikaros V2 产品需求文档（PRD）

| 项目 | 内容 |
|---|---|
| 产品名称 | Ikaros（Ίκαρος） |
| 产品版本 | V2 |
| 产品定位 | 自托管的个人数字内容管理、消费、创作与协作平台 |
| 文档版本 | v0.2 |
| 编写日期 | 2026-08-30 |
| 状态 | 草案（Draft） |

> 本文档定义 Ikaros V2 **要解决什么问题、面向谁、提供哪些能力以及产品边界是什么**。
>
> V2 是一次从零到一的整体架构与产品模型重构。V1 的代码结构、领域模型、数据库 Schema、API 与存储方式仅作为业务经验参考，不作为 V2 的兼容性约束。后续概要设计、详细设计、数据库设计与实施计划应以本 PRD 为产品基线。

---

## 1. 产品愿景

Ikaros V2 的目标不再只是管理 ACGMN 条目与本地媒体文件，而是成为一个围绕个人数字内容构建的统一平台。

用户可以在同一个系统中完成数字内容的：

- **收集**：接入本地、NAS、对象存储、远程来源与第三方服务中的内容。
- **管理**：统一组织动画、漫画、小说、电影、视频、音乐、图片、文章、笔记、文档、游戏资料与其他数字资源。
- **消费**：观看、阅读、收听和浏览内容，并连续保存进度、历史和偏好。
- **创作**：编写文章、专栏、博客、笔记和文档，管理草稿、版本与附件。
- **协作**：与受信任的用户共同编辑文档、一起观看视频、一起听音乐或围绕资源交流。
- **分享**：以可控、可撤销、有时效的方式将内容临时分享给朋友。
- **保存**：统一处理 Blob 的存储、去重、校验、分层、缓存、备份、归档与恢复。
- **扩展**：通过插件接入新的内容源、元数据源、存储、自动化、播放器或第三方服务。

Ikaros V2 最终应表现为一个可自托管、数据自主、能力可组合的 **Personal Digital Content Platform**。

## 2. V2 重构原则

### 2.1 从零设计

V2 不要求兼容 V1 的内部实现。

包括但不限于以下内容均允许重新设计：

- 领域模型
- 数据库表结构
- SQL 与约束
- API
- 权限模型
- 存储模型
- 插件接口
- 任务系统
- 搜索体系
- 前端信息架构
- 客户端交互

V1 仅用于回答“用户过去需要什么”和“哪些实践已经被证明存在价值”。

### 2.2 Resource-centric

系统中的逻辑内容以 **Resource（资源）** 为统一身份基础。

动画作品、剧集、电影、漫画、章节、小说、歌曲、专辑、图片集、文章、笔记、文档、游戏、归档包等都可以拥有统一的 Resource 身份，但不同类型仍应保留自己的业务语义和专属能力。

“统一 Resource”不等于把所有业务字段压缩为一组通用 JSON 数据。

### 2.3 HTTP-first / HTTP-native

系统能力应优先通过稳定、可组合、可被第三方调用的 HTTP 接口提供。

HTTP 是客户端、插件、自动化工具与外部集成访问 Ikaros 的主要接口。

对于实时协作、房间状态同步等不适合传统请求响应模型的功能，可以使用 WebSocket、SSE、WebRTC 等更合适的协议，但不能因此形成只能被特定官方客户端使用的封闭能力。

### 2.4 Composable Capabilities

搜索、标签、收藏、评分、评论、分享、权限、历史、进度、版本、通知、任务等能力应尽可能作为可组合的通用能力作用于不同 Resource，而不是为每一种内容类型重复实现一套类似功能。

### 2.5 Attachment 统一术语

V2 业务领域中统一使用 **Attachment（附件）** 表达与资源关联的二进制或内容对象。

`File` 不再作为项目核心领域模型名称。

文件系统中的 file/path 等词仍可作为底层技术术语存在，但不得重新演变为核心业务模型。

### 2.6 PostgreSQL-first

V2 数据库只面向 PostgreSQL 设计。

不再以 H2、MySQL 或其他数据库兼容性作为约束。后续设计可以合理利用 PostgreSQL 提供的能力，但核心业务约束必须清晰、可维护，不能为了使用高级特性而使用高级特性。

### 2.7 User-owned Metadata

用户对自己资源的人工编辑具有最高产品优先级。

第三方元数据源、插件、扫描器和自动同步任务可以补充或更新元数据，但不得在没有明确规则的情况下静默覆盖用户已经人工确认或修改的数据。

系统应能够区分“用户输入的数据”和“自动获取的数据”，为后续来源追踪、冲突处理和重新同步提供基础。

### 2.8 Stable External Identity

外部平台的 ID 只用于建立 Resource 与外部世界之间的映射，不应直接成为 Ikaros Resource 的内部身份。

同一个 Resource 可以同时对应多个外部平台身份，并且这些映射可以增加、移除或修正，而不影响 Resource 自身的内部身份。

## 3. 目标用户

| 用户类型 | 典型特征 | 核心诉求 |
|---|---|---|
| 数字内容收藏者 | 持有大量动画、漫画、小说、音乐、图片、影视或其他数字资料 | 统一整理、搜索、去重、归档、长期保存 |
| 家庭媒体与 NAS 用户 | 自建服务器、NAS、对象存储或家庭媒体中心 | 跨设备访问、播放、阅读、自动整理、可靠存储 |
| 内容创作者 | 编写文章、博客、专栏、笔记或知识文档 | 创作、版本管理、附件、发布、检索 |
| 小范围协作用户 | 与朋友、家人或小团队共享内容 | 临时分享、权限控制、共同编辑、一起看/听 |
| 开发者与高级用户 | 希望连接第三方平台或自动化工作流 | API、插件、Webhook、导入导出、自动化 |

V2 仍以 **Self-hosted** 为主要部署模式，不定位为由 Ikaros 官方提供的公网内容 SaaS。

## 4. 核心概念

### 4.1 Resource

Resource 是系统中的逻辑内容身份。

典型 Resource 包括：

- 动画 / 动画剧集
- 电视剧 / 电视剧集
- 电影
- 通用视频
- 漫画 / 漫画章节
- 小说 / 小说章节
- 音乐专辑 / 歌曲
- 图片 / 图片集
- 文章 / 专栏 / 博客文章
- 笔记
- 文档
- 游戏
- 软件、资料包或归档内容

Resource 负责表达“这是什么”，而不是“字节实际存在哪里”。

### 4.2 Attachment

Attachment 表示可被 Resource 使用或关联的内容对象，例如：

- 视频文件
- 音频文件
- 字幕
- 封面
- 图片
- 漫画页
- 电子书
- 文档附件
- 游戏安装包
- 压缩包
- 导出包

Attachment 是业务层概念，应与底层存储位置解耦。

### 4.3 Blob

Blob 表示 Attachment 对应的实际内容数据及其内容身份。

系统需要能够基于内容摘要、大小、类型等信息识别 Blob，以支持：

- 内容完整性校验
- 重复内容识别
- 去重
- 多副本
- 存储迁移
- 归档与恢复

同一个 Blob 可以被多个 Attachment 或业务场景复用，但业务层不应直接依赖某个物理路径。

### 4.4 Blob Placement / Replica

Blob 的实际存放位置是独立于 Attachment 与 Blob 身份的概念。

一个 Blob 可以同时存在于多个存储位置，例如：

```text
Attachment
    ↓
Blob
    ├── Object Storage A / Hot
    ├── Object Storage B / Warm
    └── Archive Storage / Cold
```

系统需要知道哪些 Blob 当前位于哪些存储层，并能够处理复制、迁移、恢复、失效和清理。

### 4.5 Collection

Collection 用于组织 Resource。

用户可以使用 Collection 表达：

- 媒体库
- 播放列表
- 阅读列表
- 收藏夹
- 专题
- 文件夹式组织
- 自定义集合

Collection 可以根据不同产品场景表现为列表、层级结构或动态集合。

### 4.6 Relation

Resource、Collection 与 Attachment 之间需要支持明确的关系语义。

典型关系包括：

- 包含
- 从属
- 剧集属于作品
- 章节属于作品
- 前传 / 后传
- 改编关系
- 版本关系
- 衍生关系
- 附件属于资源
- 封面属于资源
- 字幕属于视频
- 相关资源

关系必须具有明确类型，避免仅靠自由文本描述业务关联。

### 4.7 Room

Room 是多人实时场景的统一产品抽象。

典型场景包括：

- 一起看动画、电影或视频
- 一起听音乐
- 临时共享播放队列
- 房间聊天
- 房主与成员权限
- 播放状态同步

Room 不负责把同一份媒体流转发给所有成员。默认情况下，各客户端分别获取自己有权限访问的媒体内容，Room 主要负责同步状态、成员与事件。

### 4.8 Resource Lifecycle

Resource 与 Attachment 应具有明确的生命周期语义，而不是只存在“存在”和“删除”两种状态。

产品层至少需要区分：

- 正常可用
- 已归档
- 回收站 / 待删除
- 已永久清理

进入回收站或归档状态不等于立即删除 Blob。

Resource、Attachment、Revision、Share、Backup 等仍可能对 Blob 保持有效引用，因此逻辑删除与实际内容的物理回收必须解耦。

### 4.9 External Identity

Resource 可以关联一个或多个外部 Identity，例如：

- Bangumi ID
- TMDB ID
- IMDb ID
- MusicBrainz ID
- 第三方插件定义的 Provider ID

外部 Identity 必须包含明确的 Provider/Namespace，避免不同平台 ID 冲突。

外部 Identity 的增加、更新和删除不改变 Resource 本身的内部身份。

### 4.10 Metadata Provenance

系统需要能够记录重要元数据的来源（Provenance）。

元数据可能来源于：

- 用户人工输入
- 文件扫描或解析
- 导入任务
- 第三方 Metadata Provider
- 插件同步
- 系统自动生成

对于可能发生冲突的字段，系统需要能够判断当前值来自哪里，并支持用户选择保留人工修改、接受外部更新或恢复自动同步。

### 4.11 Derived Attachment

系统允许从一个原始 Attachment 派生新的 Attachment，例如：

- 视频转码版本
- 缩略图
- 图片预览图
- 音频波形
- OCR 文本
- 提取的封面
- 转换后的电子书格式
- 客户端或 Web 适配版本

派生 Attachment 应保留与来源 Attachment 的明确关系。

原始内容与派生内容必须能够区分；清理可重建的派生内容不应影响原始内容。

### 4.12 Resource / Blob Availability

系统需要以统一、可理解的状态表达 Resource 所需内容当前是否可访问。

典型状态包括：

- Available：当前可直接访问
- Cached：已有可直接使用的缓存
- Remote：内容存在，但需要从远端存储读取
- Processing：正在转码、解压、生成或处理
- Restoring：正在从冷存储 / 归档层恢复
- Missing：预期存在但没有可用副本
- Corrupted：检测到内容损坏或校验失败

具体状态模型由后续设计决定，但所有客户端应能够向用户解释“为什么当前内容不能立即使用”。

## 6. 统一资源库

### FR-LIB-01 资源统一浏览

用户应能够在统一 Library 中浏览不同类型的 Resource。

Library 至少应提供：

- 最近访问
- 最近添加
- 收藏
- 继续观看
- 继续阅读
- 继续收听
- 我的创作
- 分享给我的内容
- Collection
- 标签
- 全部资源

### FR-LIB-02 类型化视图

统一 Resource 身份不能牺牲专业内容体验。

系统应根据资源类型提供适合该类型的视图，例如：

- 动画使用海报、季度、剧集与追番信息
- 漫画使用卷、章节与阅读进度
- 音乐使用艺术家、专辑、曲目与播放队列
- 文档使用编辑状态、版本与协作者
- 图片使用网格、相册与 EXIF 等信息

### FR-LIB-03 Collection

用户应能够创建、编辑、排序、移动和删除 Collection，并将资源组织到一个或多个集合中。

### FR-LIB-04 Resource Relation

用户与插件应能够为资源建立明确关系，并在详情页查看相关资源。

### FR-LIB-05 多语言与多标题

Resource 应原生支持多标题与多语言信息，而不是把语言差异固化成少数特殊字段。

典型信息包括：

- 原始标题
- 中文标题
- 英文标题
- 罗马字 / 罗马音
- 别名
- 不同语言的描述

用户在搜索时应能够通过常见标题和别名找到同一个 Resource。

### FR-LIB-06 外部身份映射

用户、导入器与插件可以为 Resource 建立多个 External Identity。

系统不得将第三方平台 ID 直接作为 Resource 主键或永久内部身份。

### FR-LIB-07 元数据来源

对于重要元数据，系统应能够记录其来源，并在详情页或管理界面中提供必要的可解释性。

用户应能够判断某个字段是自己填写的、从文件中识别的，还是来自某个 Metadata Provider。

### FR-LIB-08 用户覆盖规则

用户人工确认或修改后的元数据默认不应被自动同步静默覆盖。

当外部来源与用户数据冲突时，应按照明确策略处理，并允许用户重新选择同步来源或恢复自动管理。

### FR-LIB-09 生命周期操作

用户应能够对支持生命周期管理的 Resource / Attachment 执行：

- 归档
- 恢复
- 移入回收站
- 从回收站恢复
- 永久删除

永久删除属于高风险操作，应清晰说明可能造成的影响。

## 7. 动画、影视与通用视频

### FR-VIDEO-01 视频资源管理

支持管理：

- 动画
- 电视剧
- 电影
- OVA / OAD / SP 等附加内容
- 用户自定义视频

支持：

- 播放进度
- 字幕选择
- 音轨选择
- 清晰度/版本选择
- 播放历史
- 继续观看
- 全屏与跨设备播放场景

### FR-VIDEO-04 字幕与相关附件

字幕、封面、海报、预览图等均以 Attachment 方式与视频 Resource 关联。

### FR-VIDEO-05 一起看

用户可以创建 Room，与受邀成员同步：

- 当前 Resource
- 播放/暂停
- 当前进度
- 播放队列
- 房间成员
- 房间消息与事件

## 12. 笔记与协作文档

### FR-DOC-01 统一文档能力

笔记、文章与协作文档可以共享基础文档能力，但产品体验允许根据场景产生不同表现。

### FR-DOC-02 编辑

支持结构化内容或富文本内容的编辑，并允许嵌入 Resource、Attachment 和链接。

### FR-DOC-03 Revision

所有重要文档编辑均应能够形成可追踪的 Revision，以支持历史查看与恢复。

### FR-DOC-04 多人协作

受授权用户可以共同编辑文档，并看到必要的协作状态。

### FR-DOC-05 评论

## 14. Attachment、Blob 与存储

### FR-STORAGE-01 Attachment 与存储解耦

业务 Resource 只能依赖 Attachment 等逻辑对象，不能把本地绝对路径、S3 Object Key 或某个存储服务地址作为业务身份。

### FR-STORAGE-02 多级对象存储为核心

Blob 的长期实际存储以 **多级对象存储** 为核心。

系统需要能够管理不同存储层级，例如：

- Hot
- Warm
- Cold
- Archive

具体层级可以映射到不同的 S3 / S3-compatible 服务、NAS 对象存储、云对象存储或归档存储。

不同部署可以只配置一个层级，也可以组合多个层级。

所有需要长期保存的 Blob 最终都应由对象存储体系中的一个或多个有效 Placement 承担持久化职责。

### FR-STORAGE-03 本地磁盘为辅助

本地磁盘主要用于：

- 上传暂存
- 下载暂存
- 转码工作区
- 解压与内容处理工作区
- 热缓存
- 离线缓冲
- 临时导出
- 对象存储不可用时的短期缓冲

本地磁盘默认不应成为所有长期 Blob 的唯一事实来源。

### FR-STORAGE-04 多副本

同一个 Blob 可以同时拥有多个 Placement / Replica。

系统应能够识别副本状态，并为后续的可靠性策略提供基础。

### FR-STORAGE-05 存储策略

系统需要为 Blob 提供可配置的存储策略基础，以支持未来根据以下条件执行自动分层：

- 访问频率
- 最近访问时间
- Blob 大小
- Resource 类型
- 用户指定策略
- 存储成本
- 副本数量

### FR-STORAGE-06 内容完整性

系统应能够通过内容摘要等方式验证 Blob 完整性，发现损坏或缺失副本。

### FR-STORAGE-07 去重

对于内容完全相同的 Blob，系统应具备避免无意义重复存储的能力。

去重不能破坏 Attachment 层面的独立业务关系和权限语义。

### FR-STORAGE-08 归档与恢复

进入冷存储或归档存储的 Blob 可以处于“需要恢复后才能访问”的状态。

客户端应获得明确状态，而不是简单表现为文件不存在。

### FR-STORAGE-09 缓存

缓存用于提升远程对象存储、大媒体与弱网络环境下的访问效率。

缓存应可淘汰、可重建，不应被视为永久唯一副本。

### FR-STORAGE-10 存储提供者扩展

存储能力应允许通过核心实现或插件扩展新的 Storage Provider。

### FR-STORAGE-11 派生 Attachment

转码、缩略图、预览、OCR、格式转换等处理结果应作为可追踪的 Derived Attachment 管理，并保留来源关系。

对于可以稳定重建的派生内容，系统可以使用比原始内容更积极的缓存和清理策略。

### FR-STORAGE-12 统一可用状态

服务端和客户端需要能够查询 Attachment / Blob 当前的可用状态。

状态必须能够区分至少以下产品语义：

- 可立即访问
- 已缓存
- 仅远程可用
- 正在处理
- 正在从归档层恢复
- 缺失
- 损坏

### FR-STORAGE-13 多级缓存体系

在对象存储分层之外，V2 引入面向访问路径的多级缓存体系。

从持久化存储向用户终端延伸，可以形成：

```text
对象存储标准 / 热存储层
        ↓
可选服务器本地磁盘缓存
        ↓
客户端本地缓存
```

可以将其理解为：

1. **一级高速访问层**：对象存储中的 Standard / Hot 等可直接读取层级。
2. **二级缓存**：服务器本地磁盘缓存，可由部署者选择是否开启以及配置容量和淘汰策略。
3. **三级缓存**：客户端缓存，用于播放、阅读、图片浏览、弱网络与离线访问优化。

这里的“缓存层级”描述访问路径，不改变数据所有权语义：对象存储 Placement 仍然负责持久化事实，本地服务器缓存和客户端缓存均属于可淘汰副本。

### FR-STORAGE-14 缓存优先访问

系统读取内容时应优先使用离用户最近且校验有效的可用副本，减少重复网络访问。

典型读取顺序可以表现为：

```text
客户端有效缓存
    ↓ miss
服务器磁盘缓存（如果启用）
    ↓ miss
对象存储 Standard / Hot
    ↓ unavailable
Warm / Cold / Archive 恢复流程
```

具体缓存算法由后续设计决定，但产品目标是 **Cache-first**：已有有效缓存时优先使用缓存，只有未命中或缓存失效时才逐级访问更远的内容层。

### FR-STORAGE-15 缓存与下载语义分离

客户端的 **Download（下载）** 与 **Cache（缓存）** 必须是两个不同的产品概念。

显式下载表示用户要求获得一个可长期离线使用、可管理、可删除的本地内容副本。

客户端缓存则是实现细节，可能是：

- 分片内容
- 转码结果
- 加密缓存
- 内部容器
- 非标准文件布局
- 仅播放器/阅读器能够理解的中间格式

因此：

- 用户显式下载的内容可以同时被缓存系统复用。
- 已下载内容可以命中客户端缓存，避免重复写入或重复传输。
- **普通客户端缓存不能被直接视为“已经下载的标准文件”。**
- 清理缓存不应等同于删除用户主动下载的内容。

产品界面需要明确区分“缓存占用”和“我的下载”。

### FR-STORAGE-16 弱网络与离线读取

当客户端存在足够的有效本地缓存或用户主动下载的内容时，应优先允许播放、阅读或浏览，而不是强制等待服务器或对象存储可达。

客户端重新联网后，应再同步播放进度、阅读进度、收藏等可同步状态。

### FR-STORAGE-17 逻辑删除与 Blob GC 分离

删除 Resource 或 Attachment 不应立即触发底层 Blob 的不可恢复删除。

Blob 的物理清理必须确认不存在仍需要保留的有效引用或保留策略，例如：

- 其他 Attachment 引用
- 文档 Revision
- 回收站中的 Resource / Attachment
- Backup
- 仍有效的 Share
- 系统保留策略
- 用户配置的最小保留时间

只有满足 GC 条件后，Blob 才可以进入物理清理流程。

### FR-STORAGE-18 GC 可审计

Blob 的物理删除属于不可逆或高风险操作。

系统应能够记录关键 GC 决策和清理结果，使管理员可以判断某个 Blob 为什么被清除，以及清理是否成功。

### FR-STORAGE-19 缓存与存储层级独立配置

对象存储的 Hot / Warm / Cold / Archive 属于持久化 Storage Tier；服务器磁盘缓存与客户端缓存属于访问加速 Cache Tier。

两者可以组合，但产品与配置界面必须明确区分，避免用户误认为删除服务器缓存等同于删除对象存储中的原始内容。

## 20. 插件、开放 API 与外部集成

### FR-PLUGIN-01 插件定位

插件是 V2 扩展能力边界的主要机制，但关键基础能力不能依赖某一个第三方插件才能运行。

### FR-PLUGIN-02 可扩展角色

插件可以扩展但不限于：

- Resource Provider
- Metadata Provider
- Storage Provider
- Renderer
- Search Provider
- Importer
- Exporter
- Automation
- Notification Provider

### FR-PLUGIN-03 外部平台

典型集成包括但不限于：

- Bangumi
- TMDB 等元数据平台
- Jellyfin / Emby 类媒体系统
- S3 / WebDAV / NAS
- Git / GitHub
- RSS
- 其他内容源

具体第三方平台不属于核心产品强依赖。

### FR-PLUGIN-04 权限隔离

插件必须明确声明和获得自己需要的系统能力，不能默认获得所有 Resource、Attachment 或用户数据的无限制访问权。

### FR-API-01 核心 API 开放

官方 Web、Desktop、Mobile 与第三方客户端应尽可能基于同一套公开核心能力构建。

不得为了官方客户端便利而长期保留第三方无法使用的关键私有接口。

### FR-API-02 API 版本化

对外 API 必须拥有明确的版本策略。

重大不兼容变更应通过新 API 版本、迁移窗口或其他明确机制发布，而不是在普通小版本升级中静默破坏现有客户端。

### FR-API-03 向后兼容

在合理的兼容周期内，升级 Ikaros 不应导致正常使用公开 API 的第三方客户端和插件立即全部失效。

具体兼容周期和弃用策略由后续 API / Plugin 设计规范定义。

### FR-PLUGIN-05 Plugin API 生命周期

插件接口需要区分：

- 稳定能力
- 实验性能力
- 已弃用能力

稳定 Plugin API 的破坏性变更需要明确的迁移路径。

### FR-API-04 Capability Discovery

客户端和插件应能够判断当前服务端支持哪些可选能力或版本，以便在不同 V2 版本之间进行兼容处理，而不是仅靠版本字符串猜测行为。

## 21. 导入、同步、导出、备份与恢复

### FR-PORT-01 导入

支持从用户已有的数据源导入 Resource、元数据和 Attachment。

### FR-PORT-02 V1 数据迁移

V2 不要求兼容 V1 Schema，但应允许后续提供独立的 V1 → V2 导入工具或迁移流程。

迁移属于数据转换，不应成为 V2 数据模型的设计约束。

### FR-PORT-03 导出

用户应能够以开放、可理解的方式导出自己的核心数据。

### FR-PORT-04 Import 与 Sync 分离

Import 与 Sync 是两个不同的产品概念。

- **Import**：把某一时刻的数据纳入 Ikaros 管理，可以是一次性操作。
- **Sync**：与外部来源建立持续关系，并在未来继续检测或接收变化。

一次 Import 不应默认意味着系统永久监控原始来源。

### FR-SYNC-01 持续同步

对于支持持续同步的数据源，用户可以建立 Sync 关系，例如：

- 对象存储 Bucket / Prefix
- NAS / 外部目录
- WebDAV
- Metadata Provider
- Jellyfin 等外部媒体平台
- 插件定义的数据源

### FR-SYNC-02 同步状态

用户应能够知道某个 Sync 当前：

- 是否启用
- 最近一次同步时间
- 最近一次同步结果
- 是否存在冲突
- 是否需要人工处理

### FR-SYNC-03 同步不得破坏用户修改

外部同步必须遵循 Metadata Provenance 与用户覆盖规则，不能因为来源发生变化就无条件覆盖用户人工维护的数据。

### FR-BACKUP-01 备份

系统应支持备份：

- PostgreSQL 中的核心数据
- 系统配置
- 必要的插件数据
- Blob/Placement 元信息
- 用户选择纳入备份范围的内容数据

### FR-BACKUP-02 恢复

备份必须对应可验证的恢复流程，而不是仅提供“导出文件”按钮。

## 22. 多端产品体验

### FR-CLIENT-01 Web

Web 端承担完整管理后台和主要内容访问能力。

### FR-CLIENT-02 Desktop

桌面端重点覆盖：

- 视频播放
- 音乐播放
- 阅读
- 本地系统集成
- 大文件操作

### FR-CLIENT-03 Mobile

移动端重点覆盖：

- 浏览与搜索
- 追番/收藏
- 视频播放
- 音乐播放
- 漫画/小说阅读
- 笔记与轻量编辑

### FR-CLIENT-04 第三方客户端

只要权限允许，第三方客户端应可以通过公开接口访问核心能力。

### FR-CLIENT-05 Offline-first 读取体验

Desktop / Mobile 在内容已经存在有效本地缓存或用户下载副本时，应优先使用本地内容。

弱网络或暂时无法连接服务器时，仍应允许用户消费已经具备离线条件的内容。

重新联网后，再同步必要的用户状态。

### FR-CLIENT-06 我的下载

用户主动触发的 Download 应作为明确、可管理的客户端功能存在。

用户能够查看：

- 已下载内容
- 下载进度
- 占用空间
- 下载失败状态
- 删除下载副本

“我的下载”不得简单等同于播放器或阅读器的内部缓存目录。

### FR-CLIENT-07 客户端缓存

客户端可以透明缓存近期访问的内容，用于降低网络消耗和提高启动速度。

客户端缓存允许采用非标准文件格式或内部数据布局，因此普通缓存不能向用户承诺为可以直接导出的原始文件。

### FR-CLIENT-08 下载复用缓存

当用户显式下载某个 Resource 时，客户端可以复用已经存在且有效的缓存数据，避免重复传输。

但最终“下载完成”的判断必须满足 Download 自己的完整性和可离线使用要求，而不是仅因为存在部分缓存就视为完成。

- 状态与反馈语言

### UX-02 响应式

Web 界面应覆盖桌面、平板和移动宽度，并根据内容密度调整布局，而不是简单缩放桌面页面。

### UX-03 内容优先

媒体库、阅读器、播放器和编辑器等高沉浸场景可以降低管理 UI 的存在感，但导航、权限和系统反馈仍需保持一致。

### UX-04 状态透明

远程 Blob、缓存命中、归档恢复、后台任务、转码、同步等异步状态必须对用户可理解，不能只表现为无限 Loading 或模糊错误。

### UX-05 存储与缓存语义透明

产品界面必须清楚区分：

- 对象存储中的持久化层级
- 服务器缓存
- 客户端缓存
- 用户主动下载
- 归档状态

用户不需要理解底层实现细节，但必须能够知道清理某项数据会不会造成永久丢失。

## 24. 非功能需求

### NFR-01 自托管与数据自主

用户能够在自己的服务器、家庭设备或云服务器上部署 Ikaros。

核心个人数据不应依赖 Ikaros 官方云服务才能访问。

### NFR-02 PostgreSQL

PostgreSQL 是 V2 唯一要求支持的关系型数据库。

### NFR-03 大规模资源

产品设计目标应覆盖至少十万级 Resource 与更大规模 Attachment 的使用场景，常用浏览和检索不能随着数据增长明显退化到不可用状态。

### NFR-04 大对象传输

视频、游戏包、归档包等大 Attachment 的访问应支持适合大对象和断点访问的方式，避免必须一次性加载完整内容。

### NFR-05 数据完整性

系统必须优先保证用户元数据、Attachment 与 Blob 引用关系的一致性，并能检测缺失或损坏的实际内容副本。

### NFR-06 安全

需要保护：

- 登录凭据
- Share Token
- 对象存储凭据
- 插件密钥
- 私有 Resource
- 管理接口

### NFR-07 可观测性

系统应提供足够的日志、任务状态和诊断信息，使用户能够判断存储、导入、同步、索引、插件与后台任务的运行状态。

### NFR-08 可扩展性

新增一种 Resource 类型、Storage Provider 或 Metadata Provider 时，不应要求修改大量无关模块。

### NFR-09 可恢复性

系统中的缓存、索引、缩略图等派生数据应尽可能可重建；关键数据必须具备明确的备份和恢复方案。

### NFR-10 API 兼容性

公开 API 与稳定 Plugin API 必须具备明确的版本、弃用与兼容策略。

普通版本升级不应无预警破坏已经依赖稳定接口的客户端和插件。

### NFR-11 多语言数据模型

核心 Resource 模型不得假设一个资源只有单一标题或单一语言描述。

国际化需求应从数据模型层具备表达能力，而不是只在 UI 文案层做翻译。

### NFR-12 缓存可重建

服务器缓存和客户端普通缓存均属于可淘汰、可重建数据。

系统不能依赖这些缓存作为唯一的数据恢复来源。

### NFR-13 审计可靠性

与权限、分享、数据永久删除、Blob GC、备份恢复有关的重要审计事件必须具有足够可靠性，避免关键操作完成后没有任何可追踪记录。

## 26. 明确的非目标

V2 当前不以以下目标为核心：

- 官方运营的公网影音内容分发平台
- 面向大规模陌生用户社交的社区产品
- 公共版权内容下载站
- 完整替代专业视频剪辑、音乐制作或图像处理软件
- 完整替代企业级多人办公套件
- 强制兼容 V1 数据库、API 或内部代码结构
- 为了兼容多个关系型数据库而限制 PostgreSQL 能力
- 将本地磁盘作为所有 Blob 的默认唯一长期存储
- 将客户端普通缓存等同于用户可管理的标准下载文件
- 将任意第三方 Provider ID 作为 Ikaros Resource 的永久内部身份

## 27. V2 产品验收原则

V2 的设计与实现应持续用以下问题进行验收：

1. 新能力是否能够围绕 Resource、Attachment 等核心概念自然组合，而不是继续形成孤立子系统？
2. 客户端和插件是否能够通过稳定接口使用核心能力？
3. 业务 Resource 是否与 Blob 的物理存储位置真正解耦？
4. 对象存储是否承担长期内容数据的核心职责，本地磁盘是否保持为辅助角色？
5. 新增内容类型时，是否可以复用搜索、标签、权限、分享、Activity、任务等通用能力？
6. 用户能否随时理解自己的内容在哪里、当前是否可访问、是否已缓存、是否已归档、是否有可靠副本？
7. 用户能否导出、备份和恢复自己的数据？
8. V2 是否避免为了兼容 V1 而保留已经不合理的抽象？
9. 用户人工维护的元数据是否能够避免被自动同步无意覆盖，并能够追踪数据来源？
10. 一个 Resource 是否可以稳定关联多个外部平台身份，而不依赖任何单一 Provider？
11. Resource / Attachment 的逻辑删除是否与 Blob 的物理 GC 正确解耦？
12. 用户是否能够清楚区分对象存储、服务器缓存、客户端缓存和主动下载？
13. 已有有效缓存时，客户端是否能够优先利用缓存，并在弱网络下继续提供合理体验？
14. 普通客户端缓存是否始终保持“可淘汰实现数据”的语义，而不会被错误承诺为标准下载文件？
15. 公开 API 和稳定插件接口是否可以在正常升级中保持可预期的兼容性？
16. 高风险权限变更、永久删除、GC 和恢复操作是否具备可追踪的审计记录？
